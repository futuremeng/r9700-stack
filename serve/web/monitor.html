Stock vLLM answers these per request only as counters, so the queue/prefill/decode split above is the mean over the window, not a per-request number — unless the monitor runs inside the serve (`serve/plugin`, mode merged), where the engine hands over each request's own split and it appears on the request row instead. For the per-request breakdown from outside: bench/ttft_breakdown.py. "Engine step" is one engine iteration (inter_token_latency_seconds) — what a client feels as one delta; "per accepted token" (request_time_per_output_token_seconds) divides it by the drafts MTP gets accepted, so with MTP=2 it reads far smaller (15.6 ms a step against 3.19 ms per token, measured 2026-11-02). A stream's tok/s is 1 / step, never 1 / per-token.
