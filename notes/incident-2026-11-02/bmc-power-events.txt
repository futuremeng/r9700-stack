## correction to `incident-2026-11-01b/mce-firmware-records.txt`: the TIME field is not the death time

Every `PROCESSOR 2:a10f11 TIME <epoch>` value in the five latched deaths is **17 s before the first journal
line of the boot that recovered it**, 5/5:

    20:36:21 -> boot 20:36:38    21:03:39 -> 21:03:56    23:52:18 -> 23:52:35
    00:04:37 -> 00:04:54         00:16:55 -> 00:17:12    00:27:11 -> 00:27:28

The TIME is stamped when the firmware writes the BERT/MCE record, i.e. during the *next* boot's POST. The
firmware cannot date a death at all. Two consequences:

- any "it hung N minutes before the reset" reading of these numbers is void;
- the BMC's `power off` record is the only external clock that can date a death, which is why the raw SEL
  (absolute times, event bytes) is worth pulling -- the paste's "N minutes ago" plus unknown paste time plus
  an unchecked BMC clock leaves minutes of slack.

## what the `oem / 登录` record is: two readings, one command decides

Reading A (human): the record is a BMC **session login**, and the pair is login then, ~1 min later, a
`power off` -- i.e. someone opened the BMC web UI and power-cycled the hung box. The order in the paste is
`oem` 1 min *before* `power off` for 6 of the 7 (4785/4786, 4787/4788, 4790/4791, 4792/4793, 4783/4784,
4781/4782), which is exactly a login-then-cycle gesture, and 4789 (`power off` with no login before it) and
4794 (`oem` with no power action after it yet) are the two edges of a session.

Reading B (firmware): the platform itself drops to a powered state on a sync flood and the `oem` record is
the BMC's per-boot record for the restart (restart cause / boot-up), 1 min after the drop.

Reading A is the better fit for the record order; reading B is the better fit for two facts: death 4
(`3b531c63`, 32 s life) left **no** firmware latch, which is what a power cut looks like rather than a fabric
reset, and death 7 recovered in 2m27 with nobody logged into the box (pi died with it) -- the boot at
00:27:28 had to come from the BMC or a button.

Decide it with, from the box (needs the operator's password):

    sudo apt-get install -y ipmitool
    sudo ipmitool -I open mc info          # which BMC, firmware version
    sudo ipmitool -I open sel info         # last record, epoch of the SEL clock
    sudo ipmitool -I open sel time get; date -u     # BMC clock vs OS clock -- do this first
    sudo ipmitool -I open sel elist        # record type + sensor number + raw event bytes
    sudo ipmitool -I open sel get <hex id from elist>   # NOT 0x4794: the UI's 4778-4794 are display
                                         # indices, not SEL record ids (see bmc-sensors-watchdog-psu.txt §2)
    sudo ipmitool -I open sdr elist | grep -i -E "power|psu|temp|intr|watchdog"
    sudo ipmitool -I open mc watchdog get  # a BMC watchdog power-off would be a different cause

and in the web UI: the **操作日志 / operation log** page (not 登录日志). A logged chassis power command with
a username and source IP settles reading A; no such command with `power off` records still present settles
reading B.
